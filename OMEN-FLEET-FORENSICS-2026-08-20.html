Two phantoms, and neither was the fault we went looking for

A stuck HEARTH queue and two unreachable Hyper-V VMs looked like one failure with one cause. They were three unrelated faults, separated by seven weeks — and one of the “missing” machines was never missing at all.

2026-08-20 OMEN · post board-swap fleet: 10 up / 0 down

01 Two stale runs held running=2 Crashed, not live
02 cc-worker-1 has no DNS Never a real node
03 cc-builder-4 on a dead subnet Retired
04 Ollama unreachable from VMs Fixed & proven

The working hypothesis was that the phantom queue entries and the unreachable VMs were the same fault. They are not related in any way. The phantom runs predate the VM problems by seven weeks, and the two VMs failed for completely different reasons — one of which is not a failure at all.

Everything below was re-verified after the board swap. OMEN now runs an Intel Core Ultra 9 285K with 127 GB of RAM and both Intel Arc Pro B70s, which moved here from AM4. The six VMs were saved rather than shut down across the swap (AutomaticStopAction = Save on all six) and auto-restored, which is why they all showed a fresh ~16 h uptime at 0% CPU while their guest clocks reached back to 2026-08-18. That idle window was the restore, not a hang.

Finding 01

The phantom runs crashed on the conductor’s first day

The two runs holding running=2 are spine-hello and spine-verify.crashed. Both are from 2026-06-30 — the conductor’s first-ever dispatch. Its own plan file says so: “This is the first live task dispatched by cc-conductor.”

They are dead, and not by file-absence alone. spine-verify’s dispatch.json names agent_pid 21313; that PID is not present, its log ~/.comms/run-spine-verify.log no longer exists, and the conductor has rebooted since (current boot 2026-08-18 03:25). No file inside either run directory has been touched since 2026-06-30 04:51 — 51 days.

Why the count could never fall on its own

This is the part worth keeping. The repo already has a phantom detector and an auto-healer — patrol and masters_pet — and they were structurally blind to these two runs. Asked to dry-run, the healer returned healable: [].

The reason is that two tools disagree about what a run is. queue_status counts every runs/*/ directory and calls it running if there’s no result.json — a universe of 187. patrol only emits a record for a directory that contains a nodes.json — a universe of 125 — and then keeps only the 60 newest. Both phantoms predate the nodes.json convention entirely, so 62 run directories are invisible to the healer while the counter still counts them.

Second, smaller convention gap

spine-verify.crashed had already been hand-triaged — someone renamed the directory with a .crashed suffix. But queue_status keys only on result.json, so the rename never released the occupancy. The human convention and the machine’s completion signal have never agreed.

Both runs are now cleared with abandoned-stubs matching masters_pet’s own schema, each carrying honest provenance and the real cause. They are reversible: delete the stub to restore the pre-heal state.

Finding 02

cc-worker-1 was never a machine

cc-worker-1.mshome.net does not resolve because no guest has ever been called that. The VM that Hyper-V displayed as cc-worker-1 is the guest claudefarm1 — an active, healthy worker and assay node that also hosts omen-worker-1’s shell. It has been up and reachable this whole time under its real name.

Two independent proofs. Its MAC, 00:15:5D:0C:C7:0A, is exactly the address assigned to claudefarm1 during the 2026-07-04 MAC-collision repair. And its console banner reads claudefarm1 login:.

mshome sibling DNS is registered by the guest over DHCP, so only claudefarm1 was ever published. Nothing in fleet.json, inventory.toml, or any scheduled task referenced the name cc-worker-1 — it existed solely as a Hyper-V label.

Correction to the record

inventory.toml states the display name “had also been changed to cc-worker-1” during the 2026-07-04 incident. It was not. HANDOFF-2026-06-27.md already calls the VM cc-worker-1, and Hyper-V records CreationTime 2026-06-27 03:17 — it was created under that label booting the golden image whose hostname is claudefarm1. The label and the hostname never matched, from day one. That note has been corrected in place.

The VM has been renamed to claudefarm1, restoring the name-equals-hostname invariant every other VM already satisfies. Display-name only, on the running machine, zero downtime.

Finding 03

cc-builder-4 was alive the whole time, and on no network at all

The guest kernel never died. Hyper-V reported Heartbeat OK and its clock was correctly time-synced. Its vNIC sat on the same Default Switch as every other VM, Status Ok. What it did not have was any presence at layer 3.

A full ping sweep of all 4,064 addresses in 172.29.64.0/20, run from cc-conductor on the same segment, found exactly five guests — and cc-builder-4’s MAC was not among them. No candidate hostname resolved either. It was not asking for DHCP at all.

The 172.21 address is a ghost record

Meanwhile cc-builder-4.mshome.net still answered 172.21.180.59 — forward and reverse — and kept answering after ipconfig /flushdns. That makes it an authoritative but stale ICS registration left over from an earlier Default Switch subnet generation, pointing at an address OMEN has no route to at all.

The Windows Default Switch regenerates its NAT prefix across host reboots. Every other VM simply re-DHCPs onto the new subnet each time. cc-builder-4 drifted across four addresses and then fell off entirely.

Root cause: it is not the fleet image

Waking its console settled it. cc-builder-4 boots to an Ubuntu desktop GDM login screen for a user named “Derek” — not the headless server image with a claude account that every other builder runs. That is also why OMEN’s key is refused there.

It boots C:\Users\derek\VMs\zen-deepseek-1\dev-vm.vhdx, a different file from the C:\Users\derek\VMs\dev-vm\dev-vm.vhdx that claudefarm1 boots. Its own manifest claims it was cloned from the claudefarm1 golden base on 2026-07-03 — which the desktop target and the “Derek” account contradict.

Not confirmed — and deliberately so

The exact guest IPv4 configuration (a pinned static address is the strong candidate) could only be read by logging into the console as Derek’s desktop account. No agent should type that password, so it stays unconfirmed. It does not change the disposition.

Hazard left behind

cc-builder-4 still holds the original golden-image MAC 00155D0CC700. A future clone off the golden image that does not regenerate its MAC will collide with it exactly as claudefarm1 did on 2026-07-03 — even now that the VM is off.

Finding 04

A live break the sweep was hiding

Turned up on the way past, and unrelated to either VM. OMEN’s Ollama is bound to 127.0.0.1:11434 only — OllamaBoot runs ollama.exe serve with OLLAMA_HOST unset. The fleet-facing lane is a separate process, OmenOllamaTracingProxy, listening on 0.0.0.0:11435.

But claudefarm1’s runner configs still pointed at :11434, so omen-worker-1 and claudefarm1’s worker shell were model-dead with ConnectionRefused. The default sweep hid it: fleet_ping probes only the first check per node unless given --all-services, and omen-worker-1’s first check is its SSH shell, which was green.

One config pointed at OMEN’s tailnet address as well — also a standing ADR-0014 violation, since machine lanes are never supposed to ride the tailnet. Both are now repointed at the fleet lane and proven with a live generate.

What changed

Every step is reversible, and backups were taken before each config edit.

  • Cleared Abandoned-stubs written for spine-hello and spine-verify.crashed on the conductor, matching masters_pet’s schema. queue_status now reads running=0, done=187. Delete a stub to undo.
  • Renamed Rename-VM cc-worker-1 → claudefarm1. Running VM, display name only, no downtime, uptime preserved.
  • Retired cc-builder-4 gracefully shut down and AutomaticStartAction set to Nothing, so it will not return on the next OMEN boot. 5.4 GB of assigned RAM reclaimed. No VHDX touched.
  • Recorded Retirement written into both views, kept separate as the repo requires: fleet.json on the conductor (build pool — retired: true, auth_status: retired, mcp_ready: false) and inventory.toml on OMEN (reachability superset — full diagnosis, dim offline rather than a permanent red DOWN).
  • Fixed Both claudefarm1 runner configs repointed to :11435; inventory checks corrected to probe the lane the fleet actually uses, with the two-lane distinction documented so the false alarm cannot come back.

Are they still needed?

claudefarm1 — yes, keep it

It is an active worker and assay node, and omen-worker-1’s shell rides on it. It needed a rename, not a retirement. (Its old coupling to omen-worker-1 remains a known fragility, unchanged by this work.)

cc-builder-4 — no

Its only role was the mixtral 8x22b q2_K overnight critic at roughly 4.2–4.4 tok/s, and it was already exclude_from_build_pool, and commandcenter/docs/adr#0029 already cut the standalone critic role in favor of am4-moe serving every role. OMEN now holds both B70s itself, which only makes a CPU-bound 4 tok/s critic VM more redundant, not less. The model is still on OMEN’s Ollama if it is ever wanted; the VM adds nothing.

Left open

Correction, 2026-08-21

An earlier version of this page said OMEN carried no B70s and an RTX 5070, and that the B70s were still on AM4. That was wrong, and it is worth recording how: it came from a single Win32_VideoController query that returned a partial enumeration listing one Intel adapter and a stale NVIDIA entry. Re-checked against Get-PnpDevice, both B70s report Status OK on distinct PCI paths, and the RTX 5070 record is a ghost with Present: False. A second source would have caught it immediately, which is the same lesson this page spends the rest of its length arguing for.

Closed since this was written

The detector gap is fixed. It was flagged here as its own task rather than patched inline, and that task landed the same day as ADR-0033, “one definition of a run”: the directory is the run, and result.json is its only terminal marker. The 62-directory blind spot is gone, and queue_status now also reports running_undispatched so a dir that never got a builder graph is visible as pure phantom occupancy rather than as work. Verified live against the gateway, not just the repo.

  • The stale DNS record. cc-builder-4.mshome.net still resolves to the unroutable 172.21.180.59 and will until the Default Switch DNS state is cleared. Harmless now that the VM is retired, but it is a trap for anyone who pings the name and believes the answer.
  • SSH to AM4 as claude. Refused with publickey denied from OMEN. fleet_ping reports AM4 up because it probes TCP, not auth — so the sweep cannot see this. Not investigated; outside this scope.
  • Stale purpose string. cc-builder-3 is still described as the “current assay node while claudefarm1 is down”. claudefarm1 is up. Left alone as pre-existing and unrelated.
