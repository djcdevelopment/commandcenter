Why this reopens vLLM

The SYCL-vs-Vulkan program parked vLLM until OMEN ran Linux. SystemPanic/vllm-windows is a native Windows port — but a CUDA one (README: "CUDA 13 + Blackwell GPU support on Windows", NCCL multi-GPU; no XPU/oneAPI/SYCL; Intel question #31 unanswered). Its value for us is the Windows build work: setup.py accepts Windows, MSVC build, winloop, spawn-only workers. Upstream vLLM's XPU platform is pure Python + torch-xpu + triton-xpu + one out-of-tree SYCL kernel package. Nobody had combined the two. OMEN already had oneAPI 2026.1 and torch-xpu Windows wheels that see both B70s. Amended reopen condition: a native Windows build path exists.

The ladder

L0 Desk done

Port is CUDA-only; assembly path named; XCCL wall verified (is_xccl_available() == False, no ccl in the toolkit); per-card shape.

L1 Env pass

torch 2.13.0+xpu + triton-xpu 3.7.2 on Python 3.12; both B70s (31.2 GB); a Triton kernel executes on xpu:0 once a C compiler is on PATH (run.cmd); fp16 4096³ matmul 37 TFLOPS.

L2 Kernels — basic pass

vllm-xpu-kernels 0.1.14.1 built with icx.exe on Windows after nine loud refusals (icpx vs icx driver, /FI for the forced include, backslash paths, uint, Level Zero SDK for ze_loader.lib, link libraries). 78-line patch on branch windows. rms_norm / fused_add_rms_norm / silu_and_mul / rotary match torch on the B70.

L2-full Kernels — FA2 + MoE + _xpu_C built + import FA2 faults the GPU

Nine more refusals: -j16 OOMs the SYCL device compile (600 attention variants → the default configs’ 37, six jobs); ssize_t; cmake cache lost on every re-configure (setup.py’s icx.EXE vs the toolchain’s icx.exe); python312.lib; empty import libs for the SHARED TLA kernel DLLs (CMAKE_WINDOWS_EXPORT_ALL_SYMBOLS); MSVC mangles __restrict. All five extensions build, install and import (kernels windows 5725348; DLLs copied beside the .pyds by hand). flash_attn_varlen_func standalone → UR_RESULT_ERROR_DEVICE_LOST, on the 2026.0 and 2026.1 runtimes alike.

L3 Engine pass

vllm serve Qwen/Qwen3-0.6B --attention-backend TRITON_ATTN --enforce-eager on :8097. Seven launch refusals fixed one at a time (hard MoE imports, a stray import uvloop in the fork's deprecated entrypoint, a vllm/ directory shadowing the package, hung parents holding ZMQ :29550, memory shared with production, FA2 selected by default). gloo picked itself for world_size=1. Correct answer, T=0 identical ×3.

L4 Production family FUNCTIONAL

JIT-only TLA rebuild changed nothing (AOT theory refuted; UR knobs inert; driver is Aug 2026) — the CUTLASS-SYCL kernels fault on this Windows driver. Routed around: --quantization moe_wna16 --moe-backend triton --attention-backend TRITON_ATTN = oneDNN int4 linears + Triton WNA16 MoE + Triton attention. Fixed on the way: auto_gptq’s hard-coded expert-bias flag (use moe_wna16), the XPU allow-list, a cp1252 banner crash, and an upstream bug where moe_wna16 rebuilds its inner GPTQ config per layer so the loader hooks never reach it (vllm-src 183cf79). Qwen3-30B-A3B-GPTQ-Int4 on one B70: 15.64 GiB in 19 s, KV 75k tokens, correct, T=0 identical ×3, needle found at 6k and 12k at ~2.0–2.4k prompt tok/s, 599 tok/s aggregate at 64 streams (19 single, eager).

L5 jobs/h + the single-stream lever L5a done

torch.compile works on Windows (60 s, inductor via cl): single 22.5–25 tok/s (eager 18.9), 592 @64 — but XPU graph capture faults on the oneDNN int4 GEMM (-cc.cudagraph_mode=none), and T=0 determinism is lost under compile. The Triton WNA16 MoE runs on a default config (no B70 table); the only donor (Strix Halo) is worse (19 / 428) — deleted. Next: an XPU port of the MoE tuner, then the SAT-L1 jobs/h shape and one instance per card.
