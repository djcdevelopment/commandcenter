## Architecture and contracts

```text
Browser (private) -> OMEN operator service -> typed action broker -> Hearth MCP
                          |                        |       -> Mechnet advice / conductor jobs
                          |                        +       -> managed model lifecycle
                          +-> AM4 dense via authenticated :8090 alias
                          +-> private run events + artifacts + rebuildable memory index
                                           \-> direct-attempt outbox -> Hearth importer
```

The OMEN operator service owns the web session and run loop. AM4's dense model is its primary planner; OMEN's ready, evidence-qualified smaller models and MoEs take bounded delegated tasks. The model proposes **typed actions** with a reason and evidence references. Deterministic broker code checks authorization, budget, live capacity, idempotency, and allowed arguments before invoking a Hearth tool or an isolated DeepAgents runner. There is no model-generated shell command or arbitrary service-setting path. The broker records rejected proposals as well as executed ones. `propose_schedule` remains advice; the operator may use its decision record to choose a builder allow-list, while the conductor still dispatches and assays the build.

Use one run contract for every lane: `run_id`, original intent, acceptance criteria, source/worktree identity, deadline, model-attempt limit, allowed actions, and terminal outcome. A run carries stable `action_id`s linked to Hearth request/job/invocation IDs, conductor `plan_id`, build receipt ID, artifact hashes, model/runtime identity, and `hardware_profile_id` when relevant. Browser API v1 is `POST /api/runs`, `GET /api/runs/{run_id}`, `GET /api/runs/{run_id}/events?after=<sequence>`, `POST /api/runs/{run_id}/cancel`, `GET /api/capacity`, and `GET /api/memory?q=...`. Submission accepts free-form intent and optional criteria/budget; absent criteria are proposed by the agent and saved before dispatch. The UI offers an automatic route and an explicit override, but every route shows the capacity evidence and reason.

The canonical operator stream is a private append-only `events.jsonl` under `hearth/var/operator/runs/<run_id>/`. Events cover intent, retrieved context, capacity snapshot, route decision, action intent, policy decision, call result, artifact, acceptance verdict, memory correction, and restoration. Extend the existing workflow event contract/ontology for these types, and keep its domain log distinct from Hearth's kernel audit ledger and execution ledger ([ADR-0010](/C:/work/commandcenter/docs/adr/0010-two-ledgers-two-bounded-contexts.md)). The timeline is a projection joining those records by IDs; it does not copy prompts into the kernel ledger or count one inference twice. Raw private prompts/responses are content-addressed artifacts, with hashes in events. Preserve every call and retry in raw records; collapse repeated status polls only in the display.

Long-lived context is a rebuildable SQLite FTS index over explicit Derek decisions, accepted ADRs, verified findings, terminal run outcomes, and artifact manifests. A model-produced claim does not become memory merely because it appeared in a response. Each planning turn gets a bounded packet: current intent, operating rules, fresh serving state, recent run state, and a small set of cited relevant records. Store the retrieval query, selected source IDs, and token count in the run. Summaries are replaceable projections; the underlying events and artifacts remain intact. A correction supersedes a derived fact without deleting its provenance. Hardware observations from an old profile cannot certify a new profile; live readiness always wins over history. Full conversation turns may be kept as private session artifacts for the UI, but only decisions and verified work enter cross-session memory.

## Working sequence and gates

**0. Freeze a safe baseline.** Record CommandCenter's committed SHA and a read-only inventory of its pre-existing dirty and untracked files. Create a clean implementation worktree, then transfer only the current Mechnet/accounting changes on which this plan depends as a named, hashed patch/file set; do not mistake committed HEAD for the live 2026-09-15 implementation. Confirm the AM4 proof's GGUF hash, CUDA build commit, GPU UUIDs, and launcher. Name a first useful artifact before starting each bounded session. Do not spend the first quarter on a synthetic matrix. **Gate:** the isolated worktree passes the existing relevant tests before new changes, its imported baseline is attributable, rollback targets exist, and no unrelated working-tree file changed.

**1. Make the measured AM4 service available.** Install the managed service and alias, then verify startup and one real completion through the authenticated LAN facade. Hold the first serving shape at 4K/one slot and use a thin operator client before UI polish. **Gate:** same GGUF SHA-256 and two UUIDs as the proof, 65/65 layers and zero CPU model-weight buffers in the active startup log, authenticated alias ready, unauthenticated request denied, rendered context check rejects overflow, service stop/start is reversible, and existing AM4 applications remain healthy. If any condition fails, do not advertise the rung.

**2. Deliver one useful agent artifact early.** Give the AM4 operator the real task: inspect the AM4 result and current Mechnet sources, then produce a short cited capacity note naming the precise catalog/snapshot gaps. This is the smoke test for local planning, tool use, context retrieval, and physical-attempt accounting. For this pilot cap the operator at 24 decision steps, 32 physical model attempts, and 1,024 output tokens per model call; the rendered 4K guard reserves the rest for input and tools. **Gate:** the note's claims match source evidence; the run contains all model attempts and tool calls; no truncated or uncited answer is accepted. If the model cannot do this within the planned cutoff, stop and ask whether to switch local model or narrow the task before building more UI apparatus.

**3. Complete the broker, memory, and web workspace.** Add the run API, typed actions, append-only events, private artifacts, retrieval index, and browser projection. Hearth is used for model lifecycle and build dispatch; the AM4 agent can choose and explain actions, but the broker enforces the rules. **Gate:** an interrupted run can be replayed after restart; duplicate action/receipt import changes no totals; corrections and old hardware evidence are handled explicitly; unauthorized browser/MCP requests fail; secrets do not appear in logs; cancellation stops new dispatch and records what was already in flight. Unit and API tests cover these cases.

**4. First complete Mechnet run.** Submit the AM4 capacity update from the web UI. Obtain a fresh resource snapshot and advisory schedule. Use two *live, qualified* local builders: prefer FX99 coder builder 2 plus builder 3 temporarily repointed to the AM4 dense alias, following the 2026-09-15 pilot's backup/restore procedure. Pause new AM4 operator inference while the one-slot AM4 builder is active. The build request requires changes to inventory, catalog/schema, backend readiness/snapshot, and scheduler tests. Harvest candidate branches, check that the required paths actually changed and satisfy the acceptance tests, compare before/after advisory placements, and leave the winner in the conductor's isolated bare mirror. Do not merge it into OMEN's working repo, push it, or deploy it. If either builder is unavailable or unqualified, do not silently substitute a metered frontier builder; report the constraint and continue only with a valid local path. **Gate:** a candidate diff, source-based acceptance review, test evidence, and complete transaction timeline exist. A conductor assay grade or mere file presence is insufficient.

**5. Tune only from accepted work.** After the first candidate is reviewed, use real queued work to compare 4K versus 8K/16K context and then one versus two slots, one variable at a time. Record per-request and aggregate goodput, accepted artifacts/hour, TTFT, context correctness, peak VRAM per card, service impact, and temperature/power only where measured. Promote a new preset only when it passes correctness, memory margin, and outcome gates; otherwise retain 1:1/4K/one slot. Do not infer GPU utilization, energy, or multi-slot capacity from token totals alone.

For the **first live end-to-end run**, use a two-hour ceiling *after* the minimal operator and AM4 service are ready: capacity note due by minute 30; at least the middle hour for the actual build; final 30 minutes reserved for review, accounting, and restoration of temporary builder settings. At each phase boundary check artifact, remaining work, projected finish, and added cost. Ask Derek promptly if no useful artifact exists by the cutoff, a gate materially overruns, the delivery reserve is threatened, or hardware/model/topology must change. The ceiling does not justify continuing a weak path.

## Acceptance checklist

- The web workspace submits one free-form intent, displays the agent's route and evidence, follows a running job, supports cancellation, and links to the final artifact and raw transaction record.
- AM4 is resident at the measured shape after normal startup, is absent from schedulable capacity when unhealthy, and is never double-counted alongside its inactive Ollama route. OMEN remains available for qualified delegated work.
- Every operator action has an intent, policy decision, result, and correlation IDs; every physical local inference attempt has a durable receipt. Retry, unknown usage, and failed deliverable remain visible and are not recast as success.
- A restarted operator retrieves an earlier explicit decision with its source, respects a correction, and refuses to use old GPU evidence as current serving proof.
- The first Mechnet run yields a reviewable AM4 dual-GPU candidate and passing relevant tests, with no merge or deployment. If the run fails, it still closes with the precise failed gate, preserved evidence, and restored temporary runner settings.
- The outcome panel reports accepted artifacts and elapsed time first. It distinguishes GPU telemetry from inference tokens, and includes agent intervention or assisted recovery attribution.
