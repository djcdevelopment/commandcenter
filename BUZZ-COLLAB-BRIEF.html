Verdict: the premise flipped, but your instinct was right — and there's a real, novel lane here.

Buzz is not a GPU swarm — it's a self-hostable human+agent collaboration workspace on a Nostr relay (Slack+GitHub-shaped, agents as first-class members; Apache-2.0, launched publicly 2026-07-21). But the peer-to-peer part you spotted is real and shipped: Buzz Mesh — relay-gated shared AI compute, built on a separate Block-authored engine mesh-llm running over iroh (authenticated NAT-traversing QUIC). Members pool GPUs; agents consume the pool as a local OpenAI-compatible endpoint; encrypted model traffic flows directly between machines — the relay introduces peers and never sees a prompt.

Two ways to plug the B70s in: Lane A (works this week) — per-friend credential in front of our existing OpenAI-compat endpoints via the proven Funnel+Caddy chain. Lane B (the experiment worth doing) — run mesh-llm on AM4 via its Linux Vulkan bundle and join his mesh with an invite token: outbound-only, no Funnel, no inbound ports. No prior art found of any Intel Arc B-series node in a mesh — we'd be first.

1 · What Buzz actually is

Self-hostable workspace where humans and agents share channels, threads, DMs, voice, code repos, and workflows — every message, review, workflow step, and git event is a signed Nostr event in one log on a relay the community owns (Rust/Axum, WebSocket + REST, Postgres/Redis/S3 behind it). Identity is per-participant Nostr keypairs; humans delegate narrowly-scoped authority to agents, which then sign their own work. Agents attach through harnesses (goose, Claude Code, Codex) via the ACP bridge — Buzz is model-agnostic; inference is the agent's concern.

2 · The P2P layer — how it actually works

Buzz relay (Nostr, friend-hosted) ── gates membership & introduces peers; NEVER carries prompts │ admission = community membership ("the same gate") ▼ mesh-llm nodes (each member's box) ── Rust binary, embedded llama.cpp-family runtime, GGUF models │ pooled catalog; route-to-loaded-peer OR split big models │ into layer-range pipeline stages across machines ▼ iroh transport ── authenticated QUIC, hole-punching + NAT traversal, relay fallback (two regions), node identity = public key, end-to-end encrypted, outbound-only from the node ▼ consumer side: agents hit http://localhost:9337/v1 — a normal OpenAI-compatible endpoint
"Buzz introduces authorized peers, then encrypted model traffic travels directly between them."— Block engineering blog
"The relay coordinates the trust, the machines do the work, and the request runs directly between them — the relay never sees a token of it."— VISION_MESH.md

Standalone vs relay-gated: mesh-llm also runs without Buzz at all — mesh-llm serve --model <GGUF> starts a mesh, --publish advertises it via Nostr discovery, and mesh-llm serve --join <token> joins a private mesh by invite token. So a "one-off key for a trusted friend" maps to either his mesh's invite token (standalone) or a scoped membership on his relay (full Buzz). Token rotation/revocation is undocumented — open question #3.

3 · Can the B70s carry a mesh node? (feasibility)

Yes, by the Vulkan lane — and nobody's done it yet. mesh-llm hosts models itself (embedded llama.cpp-family runtime, GGUF); it does not proxy an existing OpenAI endpoint, so our running llama-server can't be its capacity source — the node needs its own VRAM slice. Published bundles: Linux CPU / ARM64 / CUDA / Blackwell / ROCm / Vulkan, Windows equivalents, Metal on macOS. No SYCL bundle — Linux Vulkan is the Arc path, and llama.cpp-Vulkan on Battlemage is proven ground in the community even though no mesh-llm-on-Arc prior art exists anywhere we searched.

The tenancy question (the real cost): both B70s are fully subscribed by the resident tenant — b70-moe serving gpt-oss-120b layer-split across both cards (ADR-0018); oxen is already the pin-only alternate that requires stopping it. A mesh contribution is a third tenant profile, same pattern:

  • T1 — scheduled windows (recommended start): stop b70-moe, run mesh-llm on one/both cards for an agreed window, restore after. Fits the job-shop doctrine exactly — a mesh window is a schedulable job on sunk compute.
  • T2 — split residency: re-carve to a single-card model for am4-moe + dedicate the other B70 to the mesh long-running. Real capability cost to HEARTH; only if the collaboration proves out.
  • ⚠ Host RAM (32 GB + 8 GB zram) is AM4's binding constraint — the mesh model's GGUF load must respect it; pick models accordingly.

4 · How we'd wire it — two lanes

Lane A — credentialed endpoint (works this week)

friend's agents (Mac) │ HTTPS + per-friend key ▼ Tailscale Funnel → Caddy (one path only, 404 rest, stamps X-Hearth-Key, per-friend URL = per-caller identity) [ADR-0025 clone] ▼ HEARTH gateway :8710 — friend gets his own caller profile (callerctl, deny-by-default, generate-only scope) [ADR-0019/22] ▼ router → am4 rungs (gpt-oss-120b :8082)

Zero new software; his harnesses just add a model provider URL. Routing through HEARTH (not a raw port-forward to :8082) puts every friend call on the ledger — centralized-capture holds, and his profile can be revoked in one line. Known gap: current Caddy build has no rate-limit module (needs xcaddy + caddy-ratelimit if we care).

Lane B — mesh-llm node (the experiment)

AM4 (native Ubuntu) mesh-llm, Linux Vulkan bundle model: GGUF sized to the granted slice │ `mesh-llm serve --join <his-token>` ▼ iroh — outbound QUIC only, hole-punch, relay fallback, E2E encrypted, node identity = our public key ▼ his mesh — B70 capacity appears in his pool; his agents consume via localhost:9337/v1 on their side

No Funnel, no inbound ports, no tailnet involvement at all. Managed as a systemd tenant unit under HEARTH ops (start/stop = contribution window), OTel-wrapped so Watchfire sees it. Stretch goal once stable: stage-split hosting — a model too big for his Macs alone, split across his fleet + our B70s. That's the genuinely new capability.

5.5 · The operational envelope — what mesh-llm leaves to us

Key reframe (surfaced 2026-07-24): mesh-llm is a capacity provider, not a scheduler. Read-only inspection of its full runtime surface shows it exposes placement levers and deliberately nothing for lifecycle, priority, or multi-tenant isolation. That missing layer is exactly what our fleet already is (job-shop scheduler + ADR-0018 tenancy + offload router). So the integration is not "run mesh-llm and join" — it's "our scheduler owns the envelope; mesh-llm serves inside it."

Axis (nobody asked)What mesh-llm exposesWho owns it → our answer
Context size--ctx-size; default auto-scales to fill VRAM (why E1 grabbed 131k / 6.5 GB KV unasked)Operator. Pin a sane ceiling per contributed model — don't let it greedily eat the card.
VRAM envelope--max-vram (GB cap on planning + mesh advertisement) · --device (single-card pin) · --flavor vulkan · --no-enumerate-host (don't broadcast our hw)Ours. These are the co-existence knobs — see tenancy row.
Reset / KV lifecyclenothing — 4 lanes, no per-caller isolation, no eviction/reset surfaceUnowned risk. In a shared node, guests share slots with no tenant boundary. Mitigate by not co-mingling our callers with guests on one node.
When/how to loadload/unload = manual imperative; no lazy/on-demand/pin/TTL policy; 6.7-min cold load for big modelsOurs. Preload during a scheduled window, never lazy-load on a guest request. Load latency is a scheduler input, not a runtime surprise.
Priority / preemptionnothing — no priority, fairness, queue, or preemption; assumes the node is dedicatedOurs entirely. Guest work never preempts resident work → mesh = pin-only idle-window tenant, same class as oxen.

Tenancy options, now concrete

  • Pin-only window (default): stop the 120B (it needs both cards — cannot co-reside), give the whole box to mesh for a scheduled window, restore. Proven by E1/E4.
  • Single-card 30B = the recommended test vehicle (decided 2026-07-24): serve Qwen3-30B-A3B (~18.6 GB) pinned to one B70 via --device + explicit --ctx-size 16k (don't auto-scale-to-fill). Easier/safer (no host-RAM stacking → the OOM mode is gone), and faster than dual-card would be — a model that fits on one card avoids the 120B's per-token cross-card -sm layer sync. Gives the clean throughput number E1 still owes. Two sub-modes: (i) isolated — 120B down, mesh on one card, other idle; (ii) true co-residency — a single-card tenant (b70-critic 14B) on card A + mesh 30B on card B = owner-vs-guest on separate cards, the live governance test. Device-map RESOLVED 2026-07-24 (no ONEAPI_DEVICE_SELECTOR remap → SYCL = PCI-BDF order, all views agree): card0 0c:00.0 = Vulkan0 = SYCL0; card1 10:00.0 = Vulkan1 = SYCL1. Collision-free config: owner b70-critic (14B, SYCL1 = card1) + mesh 30B on --device Vulkan0 (card0). Hard-confirm via llama-ls-sycl-device under oneAPI env at window-open (free).
  • Proxy-in-place (unverified, high value): advanced help leaked a config url = "http://gpu-box:8000/v1" + "client-only mode" — mesh-llm may be able to front our running 120B at :8082 as a mesh capacity source with zero card allocation and nothing stopped. This would overturn the research finding that mesh-llm can't proxy an external endpoint. verify next — it could dissolve the tenancy conflict entirely
