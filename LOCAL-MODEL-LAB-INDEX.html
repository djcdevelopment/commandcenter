Local Model Labs — Index

Every hardware and local-inference experiment run on this estate, 2026-05-24 → 2026-08-05. Consumer parts only: one RTX 5070 workstation and one dual Intel Arc Pro B70 box. Each entry cites its source document, the hardware it ran on, and when.

How to read this

Numbers are quoted from the lab documents, not re-derived. Where a lab was later corrected or retracted, the correction is in the entry — not buried. Labs live in several repos; four are public on GitHub and linked as such, the rest are local paths on this machine.

Two eras, one box. The dual-B70 machine was benchmarked first on Windows 10 + Vulkan (May–June 2026), then migrated to native Ubuntu + SYCL/Level Zero (late June 2026 onward). Numbers do not carry across the migration — treat them as separate platforms.

Five findings that survived every lab

  • System RAM is the binding constraint, not VRAM. The B70 box has 64 GB of VRAM and 32 GB of DDR4. The 32 GB is what breaks first — repeatedly, across three independent labs (wind tunnel, O0 inventory, the 2026-07-30 standoff).
  • MoE is the architecture that fits consumer hardware. At equal ~32B total params and Q4 on one card, a 3B-active MoE decoded 5.7× faster than a dense 32B (130 vs 23 tok/s) — decode streams active params, so sparsity buys back the bandwidth you don't have. (denning)
  • Backend and kernel choice swing results more than the GPU does. Same model, same card: CUDA did prompt eval at 2276 tok/s, Vulkan at 68.5 — a 33× spread on identical silicon. And on Vulkan/Arc, flash attention is a pessimization (~4× slower at depth), which makes quantized KV a trap because it forces FA on. (backend lab, denning)
  • Context depth is the real cliff, not model size. Qwen3-30B-A3B on one B70 decodes at 86.9 tok/s empty and 5.3 tok/s at 64k — a 16× fall. Prompt ingest, not generation, dominates the wall clock on any long-context request. (SYCL ladder, denning roofline)
  • Local output quality held up against frontier cloud. On a scored documentation/ADR task, local gpt-oss-120b scored 93.8 vs Gemini 3.1 Pro's 90.6 and 3.5 Flash's 89.2. The cloud's only measured win was latency — about 4–5× faster. (doc-adr bench)

1.1 · Ollama backend lab — CUDA vs Vulkan vs Intel iGPU

RTX 5070 12 GB + Intel iGPU 128 GB DDR5 Windows 2026-07-02

What it tested. The same model and prompt driven through four isolated Ollama servers on separate ports — CUDA, Vulkan-on-NVIDIA, Vulkan-mixed (both GPUs visible), and Vulkan-on-Intel-iGPU — to find out what the backend choice alone is worth. Models: qwen2.5:14b and mixtral:8x22b-instruct-v0.1-q2_K.

Findings

  • CUDA is 33× faster at prompt eval than Vulkan on the same card (2276 vs 68.5 tok/s) and 1.4× at generation. The backend, not the silicon, is doing the work.
  • The Intel iGPU really can run models — including the 52 GB Mixtral, which loaded 49.6 GiB into Intel shared GPU memory and ran at 0.83 tok/s. It is a capability proof, not a lane you'd use: it left under 5 GB of free system RAM.
  • "Both GPUs visible" ≠ useful split. Vulkan-mixed enumerated both devices but placement stayed on the RTX for the small model, and on RTX + CPU-mapped RAM for the big one. Intel was never materially used.
  • Cross-service contention is survivable but expensive. With a second CUDA daemon active, qwen2.5:14b fell from ~61.9 to ~21.5 tok/s and qwen3-coder:30b fell to 4.12 tok/s — still usable, roughly half to a tenth of solo throughput.

1.3 · Hardware capability matrix — what role each model class can hold

RTX 5070 12 GB · 128 GB DDR5 Windows 2026-07-02

What it is. Not a leaderboard — a deployment map. It takes the measured numbers above and assigns each model class an operational role (resident controller / interactive specialist / batch specialist / fallback worker / overnight critic), tagging every cell measured, published, or inferred so you can see exactly which claims are backed by this rig and which are borrowed from a model card.

The operating conclusion

  • A 12 GB GPU strongly favours a control-plane / specialist split. Dense 14B-class models are plausible resident controllers; 30B–32B class models are opportunistic specialists or batch jobs.
  • The constraint is residency, not active parameters. A MoE like Qwen3-30B-A3B behaves like a small model per token but its total weights still drive placement and memory pressure.
  • Two tiers work today on one box: mid-size interactive on the RTX, plus a much larger sparse model as a background critic out of host RAM.
  • The honest part: it ships an explicit "open cells to fill next" table naming what it never measured.

1.6 · ember RnD — the planner/critic model matrix (on a 4070 Ti)

RTX 4070 Ti 12 GB GDDR6X Ollama / CUDA runs 2026-06-05 → added 2026-08-05 — missed in first sweep

What it tested. Seven numbered research documents plus a run log, exercising a planner↔critic loop across different model pairings to find where it breaks. This is the closest thing in the corpus to a genuine multi-model matrix — and it ran on a 4070 Ti, not the 5070. Worth knowing if you remember "a decent matrix of models": the 5070 work is 2 models deep and scenario-wide; this is the model-wide one.

  • Run 01 — qwen3:8b planner + llama3.2 (3B) critic: critic approved a plan in which 5 of 6 file paths did not exist. A false approval, caused by the planner getting only a README excerpt and a top-level listing. Fixed by feeding the tracked-file tree to both roles.
  • Run 02 — same models after the fix: paths all correct (the fix is model-agnostic — an 8B planner grounds fine once it can see the tree), but the loop stalled on 3B-critic noise, degrading to bare noun-phrases by round 3.
  • Run 03 — qwen3:8b planner + gpt-oss:20b critic: a strong critic is transformative — 7 specific grounded issues in round 1. But round 3 regressed, with the planner emitting a corrupted path. Open question in the doc: planner weakness, or VRAM contention from co-running a 13.6 GB model with the planner on a 12 GB card?
  • Doc 01 also carries the hardware-target reasoning for both a dual-B70 production target and the 4070 Ti rehearsal target, with quantization/VRAM budgets per role.
  • Doc 07 backfills the first planner/critic run on the B70s (2026-06-05) and one more durable operating point: gaming-coexistent inference — a large-context model serving from card 1 while a game ran on card 0, with no measurable gaming impact.

2.1 · b70tools — is Task Manager telling you the truth?

2× Arc Pro B70 32 GB Ryzen 9 5900X · 32 GB DDR4 Windows 10 Pro 2026-05-24 → 05-28 public repo

What it tested. A Windows-native telemetry tool built to answer one question: when a model is split across two 32 GB B70s, what is actually happening? It reconciles four independent sources — D3DKMT kernel adapter counters, DXGI per-process heap budgets, Vulkan VK_EXT_memory_budget, and IGCL power/thermal — via LUID-anchored identity, and tags cross-source disagreements in real time.

Findings

  • The answer was no — Task Manager wasn't telling the truth. The tool exists because the layers disagreed.
  • The two physically identical cards are not identical in software. The top-slot card runs 10–15 °C hotter VRAM under identical load and its IGCL telemetry reads physically impossible values (5.117 V and 8.55 GHz at idle) — a driver bug, not a hardware one. Both cards deliver identical inference throughput; it took several experiments to confirm that definitively.
  • Observation is nearly free: 16.6 MiB RSS, <130 ms init, 0 watchdog kicks, single 490 KB exe with zero DLL dependencies.
  • Note the MoE/dense inversion in the table: the 30B MoE generates 4× faster than the 32B dense while the dense model prompts 8× faster. Different bottlenecks.

2.2 · denning — KV-cache and MoE experts as an OS-managed resource

2× Arc Pro B70 (31.87 GiB each) 32 GB system RAM · PCIe ×8 Windows / Vulkan 1.4.348 2026-06-19 → 06-21 public repo

What it tested. The deepest lab in the set. Premise: on a fabric-less, RAM-inverted, OS-arbitrated GPU box (RAM < VRAM, no P2P, Windows VidMm arbitrating), correct LLM-state management is bandwidth-roofline admission control — and you must co-exist with an adversarial OS memory manager. Named for Peter J. Denning's working-set model. Predictions were git-committed before the data that confirmed them.

Headline results

  • The demotion cliff (H1, reproduced ×2). Once a co-tenant app pushes the GPU past its VRAM budget, VidMm involuntarily evicts a model that fits — decode collapses 5× (to 0.19×) with ~5 GB spilled to PCIe-bounced shared memory. The live budget drops from 31 GB to 15 GB under a co-tenant. You cannot pin against it: D3D12 residency priority is an intra-process hint only.
  • Decode roofline, Qwen3-30B-A3B on Vulkan: 132.8 tok/s at empty context → 74.3 @ 8K → 58.2 @ 16K → 38.0 @ 32K → 11.5 @ 64K. Roughly linear to 32K, then a superlinear cliff.
  • MoE vs dense, ~32B total / Q4 / one card: MoE (3B active) decodes 5.7× faster (130 vs 23 tok/s) and prefills 2.9× faster.
  • Flash attention is a pessimization on Vulkan/Arc — ~4× slower than default attention at depth. Because quantized KV forces FA on, q8 KV is a capacity-vs-speed trap: 2–4× slower at depth, not faster. A corrected prediction that became a real finding.
  • Restore beats re-prefill by 29× on real KV bytes (84 ms vs 2422 ms), and the advantage grows with context — 22× at 1k to 75× at 14k (24.7 s re-prefill vs 0.33 s restore).
  • The admission knee: goodput-under-SLO peaks at N*=8 (229 tok/s, all SLO met) and collapses to zero by N=10 (67 tok/s). Over-admission is worse on every axis.
  • Card→card is 6.48 GB/s ≈ 0.47× host→VRAM — host-bounced, no P2P on Windows. (Contrast the Linux number in O1, where P2P works at full wire speed.)
Retracted, honestly. The two-card symmetric replication result (1.96× by replication, 260 vs 133 tok/s) is marked PROVISIONAL / under correction: symmetric load across the display card reproducibly trips a Windows display-driver TDR (Event 4101, igfxnd — 4 resets across 2 sessions). The N-session goodput run collected across two TDRs was retracted outright. The TDR is itself the finding.

Findings

  • Disabling mmap was worth 7× on 70B prompt processing — 21.5 → 151.4 tok/s. The single biggest configuration win anywhere in this corpus, and it costs one flag. The 70B is only serviceable at all with mmap off.
  • 14B prompt throughput peaks mid-batch, not at the top: 128 tokens → 902.96 tok/s, 512 → 1254.08, 2048 → 1159.54. Generation is flat (45.09 at 32 tokens, 44.98 at 128).
  • The two cards were NOT equal in this run — Vulkan1 generated 18% faster than Vulkan0 on the identical 14B (50.09 vs 42.37). Note the tension: b70tools concluded four days later (2026-05-28) that both cards deliver identical throughput, after several experiments. Treat the 05-24 gap as pre-confirmation data, not a contradiction — but it is unresolved in the record.
  • The q8-KV phase produced no results at all. Phase B ran for 221.2 s and emitted only the loader banner; the deeper-context files (65k fp16, 131k q8) are error dumps of identical size. This is early corroboration of what denning isolated a month later — that quantized KV forces flash attention, and FA is a pessimization on Vulkan/Arc.
  • 70B fp16-KV prompt curve, where it did complete: 1024 → 186.08 tok/s, 4096 → 186.06, 16384 → 120.78.

Also in the directory: a real-log processing test (30 / 200 / 2000-line slices with results JSON), a 70B "coaching" probe, and per-server stdout/stderr for every launch.

2.5 · xpu-train — LoRA fine-tuning on the B70 PRIVATE — do not publish

Arc Pro B70 32 GB Windows · torch 2.12.1+xpu 2026-06-22 loop closed added 2026-08-05 — missed in first sweep

What it tested. The half llama.cpp cannot do. llama.cpp serves a model; this path changes its weights — on-rig LoRA fine-tuning via torch-xpu on a consumer Intel card, on native Windows, then merged and re-served through the existing Vulkan serving path. The most significant lab absent from the first sweep, because it answers a different question from everything else here: not "can I run models locally" but "can I train on this hardware".

The discovery that opened it

A vLLM-viability probe refuted its own premise: the existing environment already had torch 2.12.1+xpu working on native Windows — torch.xpu sees the B70 and matmul runs at 150 TFLOPS fp16 / 158 TFLOPS bf16, with XMX engaged and bf16 available (which the Vulkan path lacks). vLLM's real blocker on Windows was packaging, not XPU support.

The memory envelope (Phase 2, Qwen2.5-Coder-7B, bf16 LoRA r=16 all-linear)

seq · batch · grad-checkpointingPeak VRAMResult
1024 · 1 · off30.3 GiBOK (barely)

4096 · 1 · off~43 GiBOOM
2048 · 4 · off~40 GiBOOM
4096 · 1 · ON27.3 GiBOK — the envelope
8192 · 1 · ON~37 GiBOOM

Peaks above 32 GiB spilled into shared system RAM before OOM — WDDM demotion again.

Findings

  • Gradient checkpointing is mandatory, not tuning. Without it the 7B OOMs by seq-2048. With it, seq-4096 at batch 1 fits in 27.3 GiB. Beyond that needs 4-bit QLoRA.
  • A real fine-tune worked: 40.4M trainable params (0.53%), held-out loss 2.96 → 1.13 (train 2.33 → 0.91), peak 17.0 GiB, 60 updates in 108 s, 157 MB adapter.
  • The loop closed end to end: merge → f16 GGUF (14.2 GB) → Q4_K_M (4.36 GB) → served on Vulkan1 in ~6 s and generated correct code. Train on torch-xpu, serve on Vulkan.

3.6 · The gambit — stress characterization of the resident 120b

2× Arc Pro B70 · 32 GB DDR4 Ubuntu / SYCL 2026-07-18 453/453 requests OK

What it tested. The brief was blunt — "find out if it breaks before we try to build things with it." Six sweeps (A–F): concurrency ladder, context depth, decode-heavy, sustained soak, overload burst, and host-RAM pressure. 453 requests, 10-second-cadence sampling including GPU die temps.

Verdict: it didn't break anywhere reachable

  • Goodput saturates at ~26 tok/s at 4 concurrent and holds perfectly flat to 16. Oversubscription costs queue latency (~+4.4 s TTFT per queued request), never throughput. The queue is stable and fair.
  • 32 concurrent requests against 4 slots — all completed, zero errors, zero timeouts. TTFT quartiles 3.9 / 16.9 / 43.5 / 69.1 / 95.9 s: a textbook linear queue drain, max wall 105 s.
  • Prefill holds ~190–220 tok/s flat to 15k depth; decode costs ~40% at 15k (9 → 5.4 tok/s per stream).
  • Prompt cache is worth 68× — identical 8k prompt back to back: TTFT 11.8 s cold → 0.17 s warm.
  • Host-RAM pressure barely dented it. A hog stepped to 18 GiB (≈48 G demand vs 30 G physical) and decode lost ≤4% — hot expert pages won LRU, zram absorbed first, and swap I/O rode a different disk from the model mmap. Caveat stated in the doc: the hog's pages compress near-perfectly, so this is a best case for zram.
  • Thermals are a non-issue: 78 °C max GPU die at full sustained load (idle ~50), CPU 71 °C — far from the box's proven 92 °C image-gen envelope. 10-minute soak drifted −2% (noise).
The one real trap — over-limit prompts truncate SILENTLY. A deliberate 17.5k-token request against a 16k slot ceiling did not error. It returned ok, normal TTFT, normal decode — the server truncated the prompt to fit. Context loss with no signal to the caller. If you build on llama-server, you must enforce payload fit yourself; it will not refuse.

3.7 · The 2026-07-30 tenancy standoff (vertical trace)

2× Arc Pro B70 · 31.7 GiB host RAM Ubuntu / SYCL 2026-07-30 incident

What it is. Not a planned benchmark — a live incident audit, and the most instructive document in the set for anyone about to run several local models at once. Three large models (120b MoE, 30B planner, 14B critic) were all enabled as boot-persistent services on one box. They starved each other.

  • 81 crash-loop restarts of the 120b unit, each failing to allocate 26 GiB on SYCL0 — because the 30B planner was holding 17.3 GiB, leaving only 13.7 GiB free.
  • Host RAM peaked at 14.7 GiB before an OOM kill, and roughly 18 GiB went "phantom" — unaccounted memory trapped by 81 SIGKILL'd driver allocations. Crash-looping a SYCL server leaks in the driver; it took a reboot to clear.
  • Port-open ≠ model-ready. Health checks that only probed the socket reported success while the model was still loading or already dying.
  • A 120b model leaves ~4–5 GiB per card — no headroom for any second GPU tenant. Residency on consumer cards is exclusive, and has to be scheduled as such.

Resolved by hardening: systemd Conflicts=, start-rate limits, RequiresMountsFor, and an alerting unit. The eventual topology decision cut the planner and critic entirely — one model serves all roles.

4.1 · Matrix wind tunnel — does self-refinement actually help?

What it tested. Six rounds of overnight experiments on idle hardware. Does an author↔critic refinement loop improve planning output, and does it depend on which model plans vs critiques? Each cell = (planner × critic × prompt archetype × laps × ordering) → a proposal scored 0–100 by a held-out judge panel. Planner and critic ran on different physical boxes. 192 cells in the largest round.

Refinement lapsRound 4 (default judge)Round 6 (neutral judge)

Findings

  • Lap count barely matters under fair, length-neutral judging — quality sits ~82–88 across 1–4 laps. The dramatic "2 laps is the sweet spot, 4 laps collapses" arc of Round 4 was largely an artifact of the judge's brevity bias.
  • The one robust real effect: a concise author prompt ("shortest complete answer; lead with the decision") scored 90.1 vs baseline 82.1 — a small but consistent edge that survived every judge and stayed flat across laps.

  • Hardware finding, found the hard way: 32 GB of DDR4 is the binding constraint, not 64 GB of VRAM. Dropping the critic model's context from 32k to 8k freed ~7 GiB (23 → 16 GiB) and stopped the OOM kills.

The value wasn't the answer about laps — it was the method. The wind tunnel flagged an effect, corrected it, explained it, then caught its own measurement bias, entirely on idle local hardware.

4.2 · Apparatus proof and judge-variance recommendations

OMEN + AM4 traces Python 3.12 stdlib 2026-07-10 public repo

What it tested. Two follow-ons to the wind tunnel. First, whether a purely rule-based classifier over the run traces can diagnose agent failures with zero tokens (14/14 self-tests passed, runs in under a second). Second, how many judge votes it actually takes to resolve a real effect.
