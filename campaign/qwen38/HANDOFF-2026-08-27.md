## Failures found and fixes made

1. `maintenance.ps1` could not identify the elevated production server because
   Windows withheld its command line. It now also resolves a verified
   `llama-server.exe` owner from the port-8082 listener.
2. A medium-integrity shell cannot kill the elevated server directly.
   `fleet/arcserve/restart-arc.cmd` now honors
   `hearth\var\arc-maintenance.stop` as a stop-only sentinel. Maintenance uses
   the existing highest-integrity `ArcServeRestart` task, refuses to proceed if
   unrelated llama-server processes exist, holds the sentinel during the
   outage, and removes it before restore. This path entered maintenance and
   restored production successfully in live runs.
3. `server-control.ps1` assigned a missing `stopped_at` property on a
   deserialized object. It now uses `Add-Member -Force`. This was validated
   against the real stale server record; the campaign PID was gone and
   production stayed online.
4. Windows returned `$null` for the exited watchdog process's `ExitCode`, even
   though the watchdog atomically wrote a fresh `status: passed` receipt. The
   latest `invoke-leg.ps1` patch clears stale terminal receipts, treats a
   numeric nonzero exit as failure, and requires a fresh valid passed receipt
   and telemetry path when the exit code is unavailable.
5. The watchdog probe also exposed unsafe memory-property access when every
   recorded server PID is already gone. The latest `watchdog.ps1` patch now
   sums an explicit live-process array, allowing the normal health-failure
   safety path to operate.

The last two fixes above were applied immediately before stopping and have not
yet been parsed, unit-tested, locked, or exercised by the campaign. The prior
30-test Python suite passed before those two edits.
