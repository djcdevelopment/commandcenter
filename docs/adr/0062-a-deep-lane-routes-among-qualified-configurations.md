# ADR-0062: A deep lane routes among independently qualified configurations

Status: **Accepted** (2026-10-05) by Codex under Derek’s documented dev delegation, after independent Opus routing-v3 PASS. Approval recorded in ~/work/CLAUDE-APPROVED.md. Production pool activation remains gated on final-profile qualification evidence.

## Context

Bench27 needs delivery capacity across both B70s and AM4. These configurations can differ in context, serving recipe and hardware. Pooling their verdicts or treating a free execution slot as a free multi-step worker would conceal those differences. An unconditional fast-seat tokenizer also prevents the deep-only configuration from admitting work.

## Decision

A deep lane declares either the existing `backend = "name"` or a nonempty, distinct `backends = ["name", ...]` list. Declaring both is invalid. Fast and tool remain optional single-backend lanes. Callers continue to select a lane, never a backend. Explicit absent lanes and the items procedure without its readers refuse. Items also refuses a pooled deep settler; its three-role admission remains a singleton-route procedure.

A list with multiple backends admits only independently qualified configurations. The additive `delivery-procedures.v1` field `backends.<backend>.profiles.<serving_profile_sha256>` contains `families` and `all` counts with the existing distinct-accepted-brief threshold and procedure ordering. Backend aggregate counts remain compatible with legacy single-backend routing; they cannot qualify a pooled route. The exporter places unversioned fingerprints in `legacy_profiles`, never `profiles`. Only records explicitly stamped `serving-profile.v2` enter `profiles`. A singleton with no current-version profiles retains legacy aggregate selection; exporting only legacy records therefore preserves its choice. This does not preserve legacy choice once current-version profiles are present, even if those profiles have not yet reached the qualification threshold. Once current-version profiles exist, automatic procedure selection uses only its matching profile even on a single route. Counts must be exported from recorded verdicts for that backend and profile, never copied between profiles or replicas. The authoritative fingerprint is produced by `LocalWorkService._serving_profile`: an allowlisted scalar/scalar-list settings projection including `serving_profile_schema: "serving-profile.v2"` and the immutable `selected_model` identifier, serialized as sorted compact JSON and hashed with SHA-256. The manifest route also stamps that schema. Pool membership requires a nonempty engine and model, plus positive declared context tokens, parallel slots and output ceiling; thin declarations refuse. The profile includes the deliberate output budget. It identifies the declared recipe; it is not proof of actual hardware or effective serving flags, which campaign host/sizing checks must validate. A singleton route supports pinned qualification laps before the backend joins the pool.

Among qualified candidates whose declared budgets and exact tokenizer admit the request, choose the fewest outstanding local-work assignments, then fewest active execution leases, then configuration order. Awaiting-review and terminal work no longer consume an assignment. Refuse a candidate whose outstanding assignments or active leases reach its declared parallel slots. A lane with no eligible candidate refuses with each reason. A chosen qualified carry procedure that cannot run may become one_call only when one_call meets the threshold at the selected qualification level; the manifest records the fallback reason and qualifying counts. Otherwise that candidate refuses. The lane need not contain identical recipes. Pooled work without a delivery brief explicitly refuses: report verdicts are not code qualification. The campaign's pooled code-capacity portion remains unmet until a separate code-qualification source is implemented; singleton code behavior is unchanged.

Serialize selection through persisted assignment across gateway threads and processes using a separate SQLite admission lock under the operator home. Unreadable outstanding-work manifests refuse with a named LocalWorkError; this implementation still scans manifests per admission. A separate in-process admission lock and the SQLite lock serialize submissions; neither holds the reconciliation lock during tokenization or lock waiting. SQLite lock timeout becomes a named LocalWorkError. Reconciliation retains its existing locks. The mutable database is ignored by Git. This deliberately favors correct admission over parallel tokenizer throughput; tokenization is bounded by existing HTTP timeouts. Raw execution clients can still acquire a lease after selection, so execution's lease gate remains authoritative and may queue an admitted job.

Deep-only auto routing selects deep directly and tokenizes each considered candidate's full prompt. An explicit deep request and code-family auto request have no dependency on fast. Carry tokenization uses the actual system and user messages. Existing execution admission and later-stage checks remain in force; initial admission is not a guarantee that all later generated turns will fit.

The manifest records backend, model, serving profile, load snapshot, excluded candidates, selected procedure, qualification counts and table digest. An idempotent retry preserves its recorded lane/backend/procedure/table, even if route order or table changes. An in-flight retry with a missing or retired recorded provider, changed model or recipe, or conflicting procedure refuses; it never selects another provider. Awaiting-review and terminal retries validate their submitted intent, source identity, brief and recorded request fields against the saved envelope/manifest and return the saved record without current route, profile or live tokenizer checks. This includes historical unversioned records. Structural retries and carried stages keep the manifest backend.

## Consequences and deployment

No backend configurations or production table are changed by this build. Deploy after independent review, qualified final-recipe evidence, and a zero-lease door restart. Initially route qualification laps through a singleton deep route with the intended procedure pinned. Do not deploy an export containing current v2 profiles until every affected automatic singleton has met its distinct-accepted-brief threshold on its intended final model/recipe. Only then deploy current-version profile evidence and the multi-backend lane together. This sequencing prevents partially qualified v2 evidence from dropping an existing singleton from carry to one_call. Keep code and delivery verdicts separately attributable. Retain existing raw-execution capacity gates and compare effective backend participation during the capacity lap. Work-production streaming also makes length-truncated plain answers fail explicitly before candidate parsing; schema truncation reports `output_truncated`, with its existing structured-output error text. Non-OpenAI work providers refuse; no transport fallback is added.

Tests cover concurrent coordinators, heterogeneous exact admission, legacy seeding, invalid routes, missing/profile-mismatched evidence, absent fast/items refusals, lease tie-breaking, exhausted capacity and stable/refused retries. Live qualification and capacity measurements remain campaign acceptance work.
